## ⚠️ КРИТИЧЕСКОЕ ПРАВИЛО: Соответствие именования полей API

**ОБЯЗАТЕЛЬНОЕ ТРЕБОВАНИЕ**: Точное соответствие между серверными и клиентскими именами полей.

### Правило именования полей

1. **ОПРЕДЕЛИТЕ ЧТО ОТПРАВЛЯЕТ СЕРВЕР**:
   - Если сервер отправляет `createdAt`, `updatedAt` (camelCase)
   - То клиент ДОЛЖЕН использовать `createdAt`, `updatedAt`
   - НЕ `created_at`, `updated_at` (snake_case)

2. **ПРОВЕРКА ПЕРЕД РАЗРАБОТКОЙ**:
   ```typescript
   // ✅ ПРАВИЛЬНО: Проверить что отправляет API
   console.log('API Response:', response);
   console.log('Field names:', Object.keys(response.data[0]));
   
   // ✅ ПРАВИЛЬНО: Использовать точные имена полей
   const createdDate = post.createdAt; // если сервер отправляет createdAt
   
   // ❌ НЕПРАВИЛЬНО: Предполагать другое именование
   const createdDate = post.created_at; // если сервер отправляет createdAt
   ```

3. **ОБЯЗАТЕЛЬНАЯ ВАЛИДАЦИЯ**:
   - Всегда логировать структуру данных от API
   - Проверять имена полей в браузерной консоли
   - Использовать TypeScript интерфейсы для проверки типов

4. **ТИПИЧНЫЕ ОШИБКИ (ЗАПРЕЩЕНО)**:
   - Смешивание camelCase и snake_case в одном проекте
   - Предположения о именовании без проверки API ответа
   - Использование трансформации полей без необходимости

### Процедура проверки

```typescript
// 1. Всегда логировать API ответ
console.log('Raw API response:', apiResponse);

// 2. Проверить структуру первого объекта
if (apiResponse.data?.length > 0) {
  console.log('Available fields:', Object.keys(apiResponse.data[0]));
}

// 3. Использовать точные имена полей
const blogPost = {
  id: data.id,
  title: data.title,
  createdAt: data.createdAt, // НЕ data.created_at если сервер отправляет createdAt
  updatedAt: data.updatedAt  // НЕ data.updated_at если сервер отправляет updatedAt
};
```

**ПОСЛЕДСТВИЯ НАРУШЕНИЯ**: Поля будут `undefined`, что приведет к отображению "N/A" или ошибкам в UI.

**ОТВЕТСТВЕННОСТЬ**: Каждый разработчик обязан проверить точные имена полей API перед их использованием.

### Методология BEM в админ-панели

#### Стандарты реализации BEM

- **Блок**: Представляет сам компонент (например, `admin-sidebar`, `btn`, `card`)
- **Элемент**: Части компонента, обозначенные двойным подчеркиванием (например, `admin-sidebar__item`, `btn__icon`)
- **Модификатор**: Вариации блоков или элементов, обозначенные двойным тире (например, `admin-sidebar__item--active`, `btn--primary`)
- **W3C валидация**: Весь BEM CSS валидирован против спецификаций W3C CSS используя css-tree
- **Централизованный импорт**: Все стили импортированы через `main.css` для предотвращения дубликатов и обеспечения правильного каскада

#### Соглашения именования BEM

1. **Структура компонента**:
   - Каждый компонент имеет свою директорию с основным CSS файлом и index.css
   - index.css импортирует основной CSS файл компонента
   - Пример: `admin-sidebar/admin-sidebar.css` и `admin-sidebar/index.css`

2. **Именование классов**:
   - Блок: `admin-[component]` (например, `admin-sidebar`)
   - Элемент: `admin-[component]__[element]` (например, `admin-sidebar__item`)
   - Модификатор: `admin-[component]__[element]--[modifier]` (например, `admin-sidebar__item--active`)

3. **Структура импорта**:
   - Все CSS файлы компонентов импортируются через их index.css
   - Основной index.css импортирует все необходимые компоненты
   - CSS файлы специфичные для страниц импортируют только нужные им компоненты

#### Пример реализации BEM

```css
/* Блок */
.admin-sidebar {
  width: 70px;
  transition: width 0.3s ease;
}

/* Элемент */
.admin-sidebar__item {
  display: flex;
  align-items: center;

/* Элемент */

  margin-right: 1rem;

/* Элемент */

/* Модификатор */

/* Стилизация на основе состояния */

  opacity: 1;
}
```

## Система аутентификации

### JWT токен-основанная аутентификация

BlogPro использует **JWT (JSON Web Token) аутентификацию** для безопасной, stateless аутентификации пользователей.

#### Поток аутентификации

```
1. Пользователь отправляет учетные данные для входа
2. Сервер валидирует учетные данные против базы данных
3. Сервер генерирует JWT токен с ID пользователя и ролью
4. Клиент сохраняет токен в localStorage
5. Клиент включает токен в заголовок Authorization для API запросов
6. Сервер валидирует токен на защищенных эндпоинтах
7. При выходе клиент удаляет токен из localStorage
```

#### Ключевые компоненты

**Серверная сторона:**
- `server/api/auth/index.ts`: Эндпоинты аутентификации
- `server/middleware/authMiddleware.ts`: Middleware валидации JWT токена
- `server/services/authService.ts`: Логика аутентификации пользователя

**Клиентская сторона:**
- `client/src/store/auth-context.tsx`: Управление состоянием аутентификации
- `client/src/services/api/auth.ts`: API сервис аутентификации
- `client/src/services/cache/http-client.ts`: HTTP клиент с обработкой JWT токена

#### Функции безопасности

- **Хеширование паролей**: Bcrypt с солью (10 раундов)
- **Истечение токена**: 7-дневное время жизни JWT токена
- **Контроль доступа на основе ролей**: Роли администратора, редактора и пользователя
- **Верификация email**: Требуется для новых аккаунтов
- **Ограничение скорости**: Защита от атак грубой силы
- **Валидация ввода**: Валидация Zod схемы на всех эндпоинтах

#### Эндпоинты аутентификации

- `POST /api/auth/login` - Вход пользователя (возвращает JWT токен)
- `POST /api/auth/logout` - Выход пользователя (удаление токена на стороне клиента)
- `POST /api/auth/register` - Регистрация пользователя
- `GET /api/auth/me` - Получить текущего пользователя (требует JWT токен)
- `POST /api/auth/forgot-password` - Запрос сброса пароля
- `POST /api/auth/reset-password/:token` - Сброс пароля
- `GET /api/auth/verify/:token` - Верификация email

**Примечание**: Аутентификация пользователя использует поле `username` вместо `login` для согласованности базы данных.

#### Управление токенами

**Хранение**: JWT токены хранятся в `localStorage` на клиенте
**Заголовки**: Токены отправляются как `Authorization: Bearer <token>`
**Валидация**: Сервер валидирует токены используя библиотеку `jsonwebtoken`
**Очистка**: Все хранилище очищается при входе/выходе для предотвращения загрязнения

#### Контроль доступа на основе ролей

```typescript
// Функции middleware
requireAuth()     // Любой аутентифицированный пользователь
requireAdmin()    // Только пользователи-администраторы
requireEditor()   // Пользователи-редакторы и администраторы
requireRole([])   // Специфичные роли
```

#### Перенаправления при входе

- **Пользователи-администраторы**: Перенаправляются на панель управления `/admin`
- **Обычные пользователи**: Перенаправляются на страницу `/profile`
- **Резервный вариант**: Перенаправляются на домашнюю страницу `/`

### Ключевые файлы подключения API

#### Клиентская сторона

1. **HTTP клиент**

   - `client/src/services/cache/http-client.ts`: Основной HTTP клиент с интеграцией кэширования
   - Обрабатывает все API запросы с автоматическим кэшированием на основе конфигурации

2. **Модули API сервиса**

   - `client/src/services/api/*.ts`: Модули API сервиса специфичные для функций
   - Примеры файлов:
     - `client/src/services/api/blog.ts`: Методы Blog API
     - `client/src/services/api/users.ts`: Методы Users API
     - `client/src/services/api/media.ts`: Методы Media API

3. **Пользовательские хуки**

   - `client/src/admin/pages/[feature]/hooks/use[Feature]Data.ts`: Хуки данных специфичные для функций
   - Подключают компоненты к API сервисам и управляют состоянием
   - Примеры файлов:
     - `client/src/admin/pages/blog/hooks/useBlogData.ts`
     - `client/src/admin/pages/users/hooks/useUsersData.ts`

4. **React компоненты**
   - Потребляют пользовательские хуки для доступа к API данным и методам
   - Никогда не делают прямые API вызовы; всегда используют предоставленные хуки

#### Серверная сторона

1. **API маршруты**

   - `server/api/routes/*.ts`: Определения API маршрутов
   - Примеры файлов:
     - `server/api/routes/blog.ts`

2. **Контроллеры**

   - `server/api/controllers/*.ts`: Обработчики запросов
   - Примеры файлов:
     - `server/api/controllers/blogController.ts`
     - `server/api/controllers/userController.ts`

3. **Сервисы**

   - `server/services/*.ts`: Бизнес-логика и операции с базой данных
   - Примеры файлов:
     - `server/services/blogService.ts`
     - `server/services/userService.ts`

4. **Модели**
   - `server/db/models/*.ts`: Модели и схемы базы данных
   - Примеры файлов:
     - `server/db/models/blog.ts`
     - `server/db/models/user.ts`

### Поток API запроса

1. **Компонент инициирует запрос**

   - React компонент вызывает метод из пользовательского хука
   - Пример: `const { updateBlogPost } = useBlogData(); updateBlogPost(postData);`

2. **Пользовательский хук обрабатывает запрос**

   - Хук отправляет действие загрузки для обновления состояния UI
   - Вызывает соответствующий метод API сервиса
   - Обрабатывает ответ и отправляет действия успеха/неудачи

3. **API сервис делает HTTP запрос**

   - Использует HTTP клиент для выполнения фактического API вызова
   - Форматирует данные запроса и обрабатывает преобразование ответа
   - Пример: `httpClient.post('/api/blog', postData)`

4. **HTTP клиент обрабатывает запрос**

   - Добавляет заголовки аутентификации и другие общие заголовки
   - Проверяет кэш для GET запросов
   - Делает фактический fetch/axios запрос к серверу
   - Кэширует успешные GET ответы

5. **Сервер получает запрос**
   - Express router направляет запрос к соответствующему контроллеру
   - Middleware обрабатывает запрос (auth, validation, и т.д.)
   - Контроллер вызывает методы сервиса для выполнения бизнес-логики
   - Сервис взаимодействует с базой данных через модели
   - Ответ течет обратно через те же слои

### Лучшие практики

1. **Централизованная конфигурация API**

   - Базовые URL, аутентификация и общие заголовки должны быть настроены в одном месте
   - Используйте переменные окружения для API эндпоинтов

2. **Обработка ошибок**

   - Реализуйте последовательную обработку ошибок на каждом слое
   - Преобразуйте серверные ошибки в пользовательские сообщения в слое API сервиса

3. **Типобезопасность**

   - Используйте интерфейсы TypeScript для данных запроса и ответа
   - Делитесь типами между клиентом и сервером когда это возможно

4. **Стратегия кэширования**

   - Следуйте конфигурации кэширования в разделе Система кэша
   - Инвалидируйте записи кэша когда связанные данные модифицированы

5. **Тестирование**
   - Мокайте API ответы в тестах компонентов и хуков
   - Тестируйте API сервисы с мок HTTP клиентами
   - Используйте интеграционные тесты для критических API потоков

### Система кэширования

- Многоуровневая архитектура кэширования:
  - Серверный Redis кэш для API ответов и запросов к базе данных (опционально)
  - Клиентский кэш памяти с localStorage персистентностью
  - Браузерный HTTP кэш для статических ресурсов
  - **Админ-панель**: Кэширование отключено для согласованности данных, использует прямое получение данных
- Следуйте установленной конфигурации TTL (Time-To-Live) для различных типов контента:
  - Блог посты: 15 минут (клиент), 1 час (сервер)
  - Медиа файлы: 30 минут (клиент), 1 час (сервер)
  - Другие данные: 5 минут (по умолчанию)
  - **Админ данные**: Без кэширования, всегда свежие из базы данных
- Стратегии инвалидации кэша:
  - Автоматическая инвалидация при модификации данных
  - Ручная очистка кэша в админ-панели
  - WebSocket-триггерные обновления кэша для согласованности в реальном времени
- Клиентская структура:
  - `client/src/services/cache/index.ts`: Основной сервис кэширования с LRU реализацией
  - `client/src/services/cache/http-client.ts`: HTTP клиент с интегрированным кэшированием
  - `client/src/config/cache-config.ts`: Централизованная конфигурация кэша
  - `client/src/utils/cacheUtils.ts`: Утилиты управления кэшем
- Серверная структура:
  - `server/db/redis.ts`: Менеджер соединения Redis
  - `server/middleware/apiCache.ts`: Автоматическое кэширование API ответов
- HTTP заголовки кэша:
  - API эндпоинты списков: `public, max-age=60, must-revalidate`
  - Рекомендуемый контент: `public, max-age=300, must-revalidate`
  - Отдельные элементы: `public, max-age=3600, must-revalidate`
  - Статические ресурсы: `public, max-age=31536000` (1 год)
  - HTML контент: `no-cache, must-revalidate`

### CSS анализатор

Продвинутый инструмент управления и оптимизации CSS интегрированный в настройки администратора:

#### Обнаружение дубликатов
- **Умный анализ**: Идентифицирует дублирующиеся CSS правила по всем таблицам стилей
- **Сопоставление на основе свойств**: Сравнивает CSS свойства, а не только имена классов
- **Оценка сходства**: Различает между идентичными (100%) и похожими (80%+) дубликатами
- **Отслеживание местоположения файлов**: Показывает точные пути файлов и номера строк для каждого дубликата
- **Пакетные операции**: Выбор и удаление нескольких дубликатов одновременно
- **Безопасное удаление**: Всегда сохраняет первое вхождение, удаляет только дубликаты

#### W3C валидация
- **Соответствие стандартам**: Валидирует все CSS файлы против спецификаций W3C CSS
- **Категоризация ошибок**: Синтаксические ошибки, ошибки свойств и значений
- **Подробная отчетность**: Результаты валидации файл за файлом с местоположениями ошибок
- **Валидация свойств**: Проверяет CSS свойства и значения против официальных стандартов W3C
- **Обработка вендорных префиксов**: Правильно обрабатывает CSS свойства специфичные для вендоров
- **Поддержка пользовательских свойств**: Валидирует CSS пользовательские свойства (CSS переменные)

#### Оптимизация производительности
- **Уменьшение размера пакета**: Удаляет дублирующийся CSS для уменьшения общего размера файла
- **Улучшение времени загрузки**: Оптимизированный CSS приводит к более быстрой загрузке страницы
- **Эффективность обслуживания**: Идентифицирует и устраняет избыточные таблицы стилей
- **Оптимизация кэша**: Более чистый CSS улучшает эффективность кэширования браузера

#### Функции обеспечения качества
- **Анализ в реальном времени**: Мгновенная обратная связь по изменениям и добавлениям CSS
- **Функциональность обновления**: Очистка кэша и повторный анализ после модификаций
- **Безопасность резервного копирования**: Всегда поддерживает оригинальные стили при удалении дубликатов
- **Защита ключевых кадров**: Исключает ключевые кадры CSS анимации из обнаружения дубликатов
- **Анализ цепочки импорта**: Правильно обрабатывает сложные структуры CSS импорта

#### Рабочий процесс использования
1. Перейдите к Админ → Настройки → CSS анализатор
2. Нажмите "Анализировать CSS файлы" для сканирования всех таблиц стилей
3. Просмотрите группы дубликатов и результаты валидации
4. Выберите дубликаты для удаления (начните с идентичных дубликатов)
5. Используйте "Валидировать W3C" для обеспечения соответствия стандартам
6. Нажмите "Обновить" для очистки кэша и повторного анализа после изменений
